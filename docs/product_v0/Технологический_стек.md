# Технологический стек и архитектурное руководство — «Клинический компас»

**Версия:** 1.0  
**Статус:** черновик  
**Местоположение:** `docs/product/Технологический_стек.md`  
**Связь:** развивает разделы 7 и 8 ТЗ v1.0, диаграммы `diagrams.md`, Discovery-план

Документ отвечает на вопросы: с чего начать разработку, какие технологии использовать, почему Flutter для мобилки, почему Python для бэкенда прототипа, и как построить дорожную технологическую дорожную карту с учётом регуляторных ограничений (152-ФЗ, рецептурный контур concept02).

---

## 1. Общие принципы технологического выбора

| Принцип | Описание | Влияние на стек |
|---------|----------|-----------------|
| **Безопасность медицинских данных** | Персональные и медицинские данные подлежат защите по 152-ФЗ, GDPR (при наличии пациентов ЕС), требованиям к ПО медицинского назначения | Шифрование на транспорте и в покое, аудит логов, разделение контуров |
| **Офлайн-first** | Пациент должен иметь возможность отмечать дневник без интернета; данные синхронизируются при появлении соединения | Локальная база на мобилке (SQLite/Hive), оптимистичный UI, очередь синхронизации |
| **Разделение контуров** | Общий контур платформы (concept01) и рецептурный контур (concept02) должны быть изолированы на уровне кода, базы и инфраструктуры | Отдельные сервисы/네임спейсы, разные ключи шифрования, разные pipelines |
| **Быстрый прототип → regulated product** | Необходимо быстро подтвердить гипотезы (Discovery), но при этом заложить путь к регистрации ПО как медицинского изделия | Монолитный прототип на FastAPI с четкими границами модулей, которые позже выносятся в микросервисы |
| **Кросс-платформенность** | Пациенты используют iOS и Android; врачи — веб-браузер на десктопе | Flutter для мобилки, React/TypeScript для веба, общий бэкенд API |

## 2. Рекомендуемый стек технологий

### 2.1 Мобильное приложение (пациент) — Flutter

**Да, Flutter — оптимальный выбор для MVP и последующих релизов.**

| Компонент | Технология | Обоснование |
|-----------|------------|-------------|
| Фреймворк UI | **Flutter** (Dart) | Единая кодовая база для iOS и Android, быстрая разработка (hot reload), доступ к нативным API (push, камера, биометрия), хорошая производительность для интерфейса с графиками и анимациями |

### 2.2 Веб-кабинет (врач, психолог, координатор, администратор) — React + TypeScript

| Компонент | Технология | Обоснование |
|-----------|------------|-------------|
| Фреймворк | **React 18+** + **TypeScript** | Стандарт де-факто для корпоративных веб-интерфейсов, сильная типизация уменьшает ошибки в медицинских формах |
| Сборка / метафреймворк | **Vite** (прототип) / **Next.js** (production) | Быстрая сборка, SSR не обязателен для кабинета врача, но может пригодиться для landing/портала |
| Управление состоянием | **Zustand** или **Redux Toolkit** | Лёгкость для прототипа, масштабируемость для production |
| UI-компоненты | **MUI (Material UI)** или **Ant Design** | Готовые таблицы, формы, алерты — критично для быстрого MVP кабинета врача |
| Графики | **recharts** или **chart.js** | Визуализация динамики пациентов |
| Формы | **React Hook Form** + **Zod** | Валидация медицинских анкет (PHQ-9, GAD-7) на клиенте и сервере |
| Аутентификация | **OAuth2 + PKCE** / **Keycloak** (позднее) | Единый вход для врачей клиники |

### 2.3 Бэкенд — Python + FastAPI

**Да, Python с FastAPI — обоснованный выбор для прототипа и первой версии.**

| Компонент | Технология | Обоснование |
|-----------|------------|-------------|
| Язык | **Python 3.11+** | Быстрая разработка, богатая библиотечная экосистема для данных и ML (кластеризация пациентов, анализ речи — идеи 01/02) |
| Веб-фреймворк | **FastAPI** | Автоматическая OpenAPI/Swagger документация, асинхронность (async/await), высокая скорость разработки, встроенная валидация Pydantic |
| ORM | **SQLAlchemy 2.0** (async) / **Tortoise ORM** | Работа с PostgreSQL, миграции через Alembic |
| База данных | **PostgreSQL 15+** | Реляционные данные (пациенты, визиты, скрининги, назначения), ACID транзакции, JSONB для гибких схем (дневник, фармакология) |
| Кэш и очереди | **Redis 7+** + **Celery** | Кэш сессий, отложенные задачи (отправка алертов, уведомлений, генерация отчётов) |
| Аутентификация | **FastAPI Users** + **JWT** (прототип) / **Keycloak** (production) | Разделение ролей (пациент, врач, админ), access токены |
| Файловое хранилище | **MinIO** (Self-hosted S3) / **AWS S3** | Хранение PDF-отчётов, экспорта, сканов согласий |
| Документация API | **Swagger UI** (автоматически из FastAPI) | Важно для интеграции с МИС и для внешних разработчиков |

**Почему Python/FastAPI для прототипа:**
- Скорость разработки функционала скрининга, дневника, алертинга — критична на этапе Discovery (6 недель).
- Легко интегрировать Python-библиотеки для анализа данных (pandas, scikit-learn) — если потребуется кластеризация или анализ речи (идеи 01/02).
- FastAPI дает production-готовый код, который не нужно будет переделывать при масштабировании.

**Ограничение:** Python медленнее Go/Node.js при высоких нагрузках, но для MVP и пилота (20–50 пациентов, 5–10 врачей) этого достаточно. При необходимости отдельные сервисы можно переписать на Go.
| Локальное хранилище | **Hive** или **SQLite (sqflite)** | Офлайн-first: хранение дневника, отметок, результатов скрининга на устройстве; синхронизация с бэкендом при появлении сети |
| Управление состоянием | **Riverpod** или **Bloc** | Предсказуемое состояние, легкость тестирования, разделение бизнес-логики от UI |
| Сетевой клиент | **Dio** + **retrofit** | REST API с перехватчиками токенов, повторными попытками, отменой запросов |
| Аутентификация | **Firebase Auth** (прототип) / **OAuth2 + PKCE** (production) | Быстрый старт, позже замена на собственную интеграцию с МИС/Active Directory |
| Push-уведомления | **Firebase Cloud Messaging (FCM)** | Надежная доставка напоминаний о дневнике и алертах |
| Графики | **fl_chart** | Визуализация динамики настроения, тревоги, сна |
| Безопасность | **flutter_secure_storage** | Хранение токенов и чувствительных данных в Keychain/Keystore устройства |

**Почему не нативная разработка (Swift/Kotlin):** удвоение команды, удвоение бюджета на MVP, более медленные итерации при проверке гипотез.  
**Почему не React Native:** Flutter дает более стабильный UI без зависимости от нативных компонентов, проще обеспечивать одинаковый опыт на iOS/Android для медицинского приложения.

**Ограничение:** Flutter-приложение нужно будет сертифицировать отдельно как часть ПО медицинского назначения (если будет заявлен рецептурный статус). Для MVP это не блокер.

### 2.4 Инфраструктура и DevOps

| Компонент | Технология | Обоснование |
|-----------|------------|-------------|
| Контейнеризация | **Docker** | Единые окружения для разработки, тестирования и продакшена |
| Оркестрация (MVP) | **Docker Compose** | Простота развёртывания на одном сервере клиники |
| Оркестрация (production) | **Kubernetes** (опционально) | При масштабировании на много клиник |
| CI/CD | **GitHub Actions** / **GitLab CI** | Автоматические тесты, сборка образов, деплой |
| Мониторинг | **Prometheus** + **Grafana** | Метрики приложения, здоровья базы, очереди Celery |
| Логирование | **ELK stack** (Elasticsearch, Logstash, Kibana) / **Loki** | Аудит действий врачей (требование 152-ФЗ) |
| Reverse proxy | **Nginx** / **Traefik** | Терминация SSL, балансировка нагрузки |

### 2.5 Интеграции

| Назначение | Технология / стандарт | Примечание |
|------------|----------------------|------------|
| МИС / ЭМК | **FHIR (R4)**, HL7 v2 | На этапе «Позднее» — интеграция с существующими системами клиник |
| Реестр лекарств (ГРЛС) | **REST API ГРЛС** (Росздравнадзор) / скриншоты инструкций | Для экрана инструкций препаратов (включая «Авиандр» из case_info) |
| Push / SMS | **FCM**, **Twilio** / российские SMS-шлюзы | Напоминания о дневнике, алерты врачам |
| Электронная подпись | **CryptoPro** / **Госуслуги API** | Для подписания согласий и клинических документов (если потребуется юридическая сила) |

## 3. Архитектурное разделение контуров (общий vs рецептурный)

Следуя concept01 (платформа скрининга и сопровождения) и concept02 (рецептурный цифровой терапевтический модуль), предлагается следующее разделение:

```
┌─────────────────────────────────────────────────────────────┐
│                     ОБЩИЙ КОНТУР (concept01)                │
│  • Мобильное приложение пациента (базовый функционал)       │
│  • Веб-кабинет врача (скрининг, дневник, упражнения)        │
│  • Бэкенд FastAPI (базовая аутентификация, данные пациентов)│
│  • PostgreSQL (общая схема)                                 │
│  • Не является рецептурным ПМИ                              │
└─────────────────────────────────────────────────────────────┘
                          │ API boundary
┌─────────────────────────────────────────────────────────────┐
│                 РЕЦЕПТУАРНЫЙ КОНТУР (concept02)              │
│  • Модуль назначения и отслеживания приёма препаратов        │
│  • Интеграция с ГРЛС, проверка взаимодействий                 │
│  • Отдельная схема БД (изоляция данных)                      │
│  • Отдельные ключи шифрования                                │
│  • Может быть зарегистрировано как ПМИ отдельно               │
└─────────────────────────────────────────────────────────────┘
```

**Преимущества:**
- Общий контур можно запускать быстрее, без полной регуляторной сертификации как ПМИ.
- Рецептурный контур изолирован: проще сертифицировать только его как рецептурное цифровое терапевтическое изделие (по аналогии с Rejoyn в США).
- Данные между контурами обмениваются через строго определенные API-контракты.

## 4. Безопасность и соответствие требованиям

| Требование | Решение в стеке |
|------------|-----------------|
| 152-ФЗ (Персональные данные) | Шифрование в покое (PostgreSQL pgcrypto), шифрование в транспорте (TLS 1.3), аудит логов всех действий, хранение данных на территории РФ (локальный сервер или российское облако) |
| GDPR (при необходимости) | Права на удаление/экспорт данных, согласие на обработку, данные минимизация |
| IEC 62304 (ПО медицинского назначения) | Контроль версий, управление изменениями, тестирование, документация рисков — на этапе подготовки к регистрации |
| IEC 81001-5-1 (Кибербезопасность) | Сегментация сети, управление уязвимостями, мониторинг инцидентов |
| FDA / Регистрация РФ (ПМИ) | Класс риска определяется на этапе регуляторной оценки (см. Discovery-план); рецептурный контур — более высокий класс риска |

## 5. С чего начать: пошаговый план (первые 4–8 недель)

### Неделя 1: Подготовка и инфраструктура
1. Создать Git-репозиторий с монолитной структурой: `apps/mobile` (Flutter), `apps/web` (React), `apps/api` (FastAPI), `infra` (Docker Compose).
2. Настроить Docker Compose с PostgreSQL, Redis, MinIO.
3. Развернуть базовый CI/CD (GitHub Actions): линтинг, тесты, сборка образов.
4. Определить схему базы данных (минимальная): пользователи, роли, пациенты, скрининги, дневник, упражнения.

### Неделя 2: Бэкенд MVP (Python/FastAPI)
1. Реализовать аутентификацию и авторизацию (JWT, роли: пациент, врач, админ).
2. Реализовать API скрининга PHQ-9/GAD-7 (создание, получение, интерпретация).
3. Реализовать API дневника (CRUD отметок, офлайн-синхронизация через флаг `last_synced_at`).
4. Реализовать API алертов (проверка критических симптомов, уведомление врача).
5. Поднять Swagger UI для документации API.

### Неделя 3: Мобильное приложение (Flutter)
1. Экран приветствия и онбординга с заявлением «не является диагнозом».
2. Экран регистрации с согласиями (152-ФЗ).
3. Экран скрининга PHQ-9/GAD-7 (вопросы, прогресс-бар, результат).
4. Экран микро-отметки дневника (одно касание, ≤ 5 сек).
5. Локальное хранилище Hive/SQLite для офлайн-режима.
6. Интеграция с бэкендом (аутентификация, скрининг, дневник).

### Неделя 4: Веб-кабинет врача (React/TypeScript)
1. Дашборд врача со списком пациентов и алертами.
2. Карточка пациента с историей скринингов и дневника.
3. Экран назначения упражнений (поведенческая активация, дневник мыслей).
4. Экран отчёта о динамике перед визитом (PDF-экспорт).

### Неделя 5: Тестирование и Discovery
1. Внутреннее тестирование всех критических путей (регистрация → скрининг → дневник → алерт → кабинет врача).
2. Проведение интервью с 2–3 врачами и 3–5 пациентами (см. Discovery-план).
3. Исправление критических багов.

### Неделя 6–8: Пилот в одной клинике
1. Развёртывание на сервере клиники (Docker Compose).
2. Обучение 2–3 врачей (≤ 30 минут на роль).
3. Подключение 10–20 пациентов.
4. Сбор обратной связи и метрик (Activation Rate, Weekly Check-in Rate, Clinic Adoption Rate).
5. Принятие решения go/no-go на этап Релиз 2.

## 6. Дорожная карта технологического развития

| Этап | Срок | Технологические цели |
|------|------|---------------------|
| **MVP** | Недели 1–8 | Монолит FastAPI + Flutter (iOS/Android) + React веб. PostgreSQL, Redis, Docker Compose. Офлайн-first на мобилке. |
| **Релиз 2** | Месяцы 3–6 | Выделение сервиса уведомлений (Celery → отдельный сервис), интеграция с МИС (FHIR), голосовой ввод (идея 01), кластеризация пациентов (идея 02). |
| **Пилот** | Месяцы 6–9 | Масштабирование на несколько клиник, Kubernetes (опционально), расширенная аналитика, админ-панель клиники. |
| **Регистрация ПМИ** | Месяцы 9–18 | Рецептурный контур выносится в отдельный regulated сервис, документация IEC 62304, кибербезопасность IEC 81001-5-1, сертификация. |

## 7. Риски технологического выбора и меры снижения

| Риск | Вероятность | Воздействие | Мера снижения |
|------|-------------|-------------|---------------|
| Flutter не пройдет сертификацию как часть ПМИ | Средняя | Высокое | Разделять общий и рецептурный контуры; Flutter используется только в общем контуре на старте |
| Python/FastAPI не выдержит нагрузки при росте | Низкая | Среднее | Профилирование на раннем этапе, возможность вынести критичные сервисы на Go |
| Зависимость от Firebase (Auth, FCM) | Средняя | Среднее | Абстракция слоя аутентификации и push через интерфейсы; миграция на собственное решение в Релиз 2 |
| Проблемы с офлайн-синхронизацией дневника | Средняя | Высокое | Тщательное тестирование конфликтов синхронизации, стратегия «последняя запись побеждает» с флагом `synced_at` |
| Интеграция с ГРЛС нестабильна | Высокая | Среднее | Кеширование карточек препаратов локально, резервный источник (ручной ввод врачом) |

## 8. Итоговая рекомендация

| Слой | Рекомендация | Причина |
|------|--------------|---------|
| Мобилка (пациент) | **Flutter** | Быстрая кроссплатформенная разработка, офлайн-first, один код для iOS/Android |
| Веб (врач/админ) | **React + TypeScript** | Стандарт для кабинетов, быстрый MVP, хорошая экосистема компонентов |
| Бэкенд прототипа | **Python + FastAPI** | Скорость разработки, автоматическая документация API, просто интегрировать аналитику |
| База данных | **PostgreSQL + Redis** | Надежность, ACID, кэш и очереди |
| Инфраструктура | **Docker Compose → Kubernetes** | Простой старт, путь к масштабированию |
| Развертывание | **Локальный сервер клиники / российское облако** | Соблюдение 152-ФЗ, хранение данных в РФ |
