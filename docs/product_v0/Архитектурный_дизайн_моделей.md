**Версия:** 1.0  
**Статус:** черновик

Документ детализирует внутреннее устройство платформы: границы сервисов, доменную модель (сущности и связи), механизмы взаимодействия между сервисами (REST + события), ключевые классы/модели данных и схему базы данных. ## 1. Обзор сервисной архитектуры

Платформа строится как модульный монолит на этапе MVP с четкими границами модулей, которые позже можно вынести в отдельные сервисы. Все модули общаются через общий API-шлюз (FastAPI) и шину событий (Redis + Celery).

### 1.1 Список сервисов/модулей

| Модуль | Ответственность | Контур | Технология |
|--------|----------------|--------|------------|
| **auth-service** | Аутентификация, авторизация, JWT, профили пользователей, роли | Общий | FastAPI + SQLAlchemy |
| **patient-service** | Данные пациентов, карточки, регистрация, согласия (152-ФЗ) | Общий | FastAPI + SQLAlchemy |
| **screening-service** | PHQ-9, GAD-7 и другие скрининги, интерпретация результатов | Общий | FastAPI + SQLAlchemy |
| **diary-service** | Микро-отметки дневника, графики, офлайн-синхронизация | Общий | FastAPI + SQLAlchemy |
| **program-service** | Назначенные упражнения, программы сопровождения, приверженность | Общий | FastAPI + SQLAlchemy |
| **alert-service** | Обнаружение критических симптомов, алерты врачу, план безопасности | Общий | FastAPI + Celery |
| **medication-service** | Рецептурный контур: препараты, ГРЛС, взаимодействия, приверженность | Рецептурный (concept02) | FastAPI + SQLAlchemy (изолированная схема) |
| **notification-service** | Push (FCM), SMS, email-уведомления | Общий | FastAPI + Celery |
| **report-service** | Генерация отчётов о динамике, PDF-экспорт, аналитика клиники | Общий | FastAPI |
| **admin-service** | Управление ролями, правами, тарификацией, настройками клиники | Общий | FastAPI |

### 1.2 Механизмы взаимодействия

| Тип взаимодействия | Механизм | Описание |
|-------------------|----------|----------|
| Синхронный запрос-ответ | **REST over HTTP (JSON)** | Клиент → API-шлюз → модуль. Все эндпоинты документируются через OpenAPI/Swagger. |
| Асинхронные события | **Redis Pub/Sub + Celery** | Например, создание отметки дневника публикует событие `diary.entry.created`, на которое подписывается `alert-service`. |
| Изоляция контуров | **Раздельные схемы БД + отдельные API-ключи** | Рецептурный контур не имеет прямого доступа к таблицам общего контура; обмен только через DTO и строго определённые контракты. |
| Офлайн-синхронизация | **Оптимистичная репликация + флаг `synced_at`** | Мобильный клиент хранит локально (Hive/SQLite), при появлении сети отправляет пакет изменений с метками времени. |

## 2. Доменная модель: сущности и связи

Ниже представлена логическая схема данных. Сущности разделены по контурам. Первичные ключи — UUID. Временные метки — UTC ISO-8601.

### 2.1 Общий контур (concept01)

#### Сущность `User` (пользователь системы)
| Поле | Тип | Описание |
|------|-----|----------|
| `id` | UUID | PK |
| `email` | String | Уникальный email |
| `password_hash` | String | bcrypt/argon2 |
| `role` | Enum | `patient`, `doctor`, `psychologist`, `coordinator`, `clinic_admin`, `super_admin` |
| `is_active` | Boolean | Активен ли аккаунт |
| `created_at` | DateTime | Дата создания |
| `updated_at` | DateTime | Дата последнего обновления |
| `last_login_at` | DateTime | Дата последнего входа |

**Связи:**
- `User` 1:N `PatientProfile` (если пользователь — пациент)
- `User` 1:N `DoctorProfile` (если пользователь — врач/психолог)
- `User` 1:N `AuditLog` (все действия пользователя)

## 4. Ключевые классы и модели данных

Ниже приведены упрощённые определения моделей на Python (Pydantic v2, используемые в FastAPI) и Dart (для Flutter). Полная реализация включает валидаторы, сериализацию и ORM-маппинг.

### 4.1 Python (бэкенд, Pydantic v2) — базовые модели

```python
from uuid import UUID
from datetime import datetime, date
from enum import Enum as PyEnum
from typing import Optional, List, Any
from pydantic import BaseModel, Field, ConfigDict


class UserRole(str, PyEnum):
    PATIENT = "patient"
    DOCTOR = "doctor"
    PSYCHOLOGIST = "psychologist"
    COORDINATOR = "coordinator"
    CLINIC_ADMIN = "clinic_admin"
    SUPER_ADMIN = "super_admin"


class ScreeningType(str, PyEnum):
    PHQ9 = "PHQ-9"
    GAD7 = "GAD-7"
    COMBINED = "combined"


class ScreeningInterpretation(str, PyEnum):
    MINIMAL = "minimal"
    MILD = "mild"
    MODERATE = "moderate"
    SEVERE = "severe"


class AlertSeverity(str, PyEnum):
    MANDATORY = "mandatory"
    ADVISORY = "advisory"


class AlertStatus(str, PyEnum):
    NEW = "new"
    ACKNOWLEDGED = "acknowledged"
    RESOLVED = "resolved"
    DISMISSED = "dismissed"


class UserBase(BaseModel):
    email: str
    role: UserRole
    is_active: bool = True


class UserCreate(UserBase):
    password: str = Field(min_length=8)


class UserRead(UserBase):
    id: UUID
    created_at: datetime
    updated_at: datetime
    last_login_at: Optional[datetime] = None

    model_config = ConfigDict(from_attributes=True)


class PatientProfileBase(BaseModel):
    first_name: str
    last_name: str
    middle_name: Optional[str] = None
    birth_date: date
    phone: str
    emergency_contact_name: Optional[str] = None
    emergency_contact_phone: Optional[str] = None
    clinic_id: UUID
    consent_personal_data: bool = False
    consent_medical_data: bool = False
    consent_data_sharing_with_doctor: bool = False


class PatientProfileCreate(PatientProfileBase):
    pass


class PatientProfileRead(PatientProfileBase):
    id: UUID
    user_id: UUID
    created_at: datetime
    updated_at: datetime

    model_config = ConfigDict(from_attributes=True)


class ScreeningResultBase(BaseModel):
    patient_id: UUID
    screening_type: ScreeningType
    score: int
    interpretation: ScreeningInterpretation
    completed_at: datetime
    answers_json: dict[str, Any]
    is_critical: bool = False


class ScreeningResultCreate(ScreeningResultBase):
    pass


class ScreeningResultRead(ScreeningResultBase):
    id: UUID
    created_at: datetime

    model_config = ConfigDict(from_attributes=True)


class DiaryEntryBase(BaseModel):
    patient_id: UUID
    recorded_at: datetime
    mood_score: int = Field(ge=1, le=5)
    anxiety_score: int = Field(ge=1, le=5)
    sleep_quality: str
    energy_level: str
    activity_level: str
    note: Optional[str] = Field(max_length=200, default=None)


class DiaryEntryCreate(DiaryEntryBase):
    device_id: str


class DiaryEntryRead(DiaryEntryBase):
    id: UUID
    synced_at: Optional[datetime] = None
    created_at: datetime
    updated_at: datetime

    model_config = ConfigDict(from_attributes=True)


class AlertBase(BaseModel):
    patient_id: UUID
    alert_type: str
    severity: AlertSeverity
    triggered_by: str
    trigger_data_json: dict[str, Any]


class AlertCreate(AlertBase):
    pass


class AlertRead(AlertBase):
    id: UUID
    status: AlertStatus
    notified_at: Optional[datetime] = None
    acknowledged_at: Optional[datetime] = None
    resolved_at: Optional[datetime] = None
    created_at: datetime

    model_config = ConfigDict(from_attributes=True)


class MedicationBase(BaseModel):
    grls_id: str
    trade_name: str
    inn: str
    dosage_form: str
    strength: str
    indications: Optional[str] = None
    contraindications: Optional[str] = None
    dosage_regimen: Optional[str] = None
    side_effects: Optional[str] = None
    interactions_warning: Optional[str] = None


class MedicationRead(MedicationBase):
    id: UUID
    grls_updated_at: datetime
    is_active: bool

    model_config = ConfigDict(from_attributes=True)


class PrescriptionBase(BaseModel):
    patient_id: UUID
    doctor_id: UUID
    medication_id: UUID
    dosage_prescribed: str
    frequency_prescribed: str
    start_date: date
    end_date: Optional[date] = None
    status: str = "active"


class PrescriptionCreate(PrescriptionBase):
    pass


class PrescriptionRead(PrescriptionBase):
    id: UUID
    created_at: datetime

    model_config = ConfigDict(from_attributes=True)
```

### 4.2 Dart (Flutter, ключевые модели)

```dart
import 'package:freezed_annotation/freezed_annotation.dart';

part 'user.freezed.dart';
part 'user.g.dart';

@freezed
class User with _$User {
  const factory User({
    required String id,
    required String email,
    required String role,
    required bool isActive,
    required DateTime createdAt,
    required DateTime updatedAt,
```

## 5. Сценарии взаимодействия (секуенс-диаграммы в тексте)

### 5.1 Скрининг и автоматический алерт

```
Пациент (Flutter)              API-шлюз (FastAPI)      screening-service      alert-service      notification-service      Врач (React)
     │                            │                      │                 │                      │                 │
     ├─POST /screenings ─────────▶│                      │                 │                      │                 │
     │                            ├─POST /screenings ───▶│                 │                      │                 │
     │                            │                      │◀──201 + id ───│                      │                 │
     │                            │◀──201 + id ─────────▶│                 │                      │                 │
     │                            │                      │                 │                      │                 │
     │                            │                      │  (если is_critical)│                      │                 │
     │                            │                      │────Event: alert.created───▶│                 │
     │                            │                      │                 │◀──ack ─────────────│                 │
     │                            │                      │                 │────POST /notifications─▶│                 │
     │                            │                      │                 │                      │◀──Push/Email ─│
```

**Описание:**
1. Пациент проходит скрининг PHQ-9/GAD-7 в мобильном приложении.
2. API-шлюз передаёт запрос в `screening-service`, который сохраняет `ScreeningResult`.
3. Если `is_critical == true`, `screening-service` публикует событие `alert.created` в Redis.
4. `alert-service` создаёт запись `Alert` со статусом `new` и severity `mandatory`.
5. `notification-service` отправляет push/email уведомление врачу.
6. Врач видит алерт в веб-кабинете, подтверждает прочтение (`acknowledged`), система фиксирует время в `acknowledged_at`.

### 5.2 Офлайн-синхронизация дневника

```
Пациент (Flutter, офлайн)      API-шлюз (FastAPI)      diary-service      alert-service
     │                            │                      │                 │
     │  (отметка сохранена локально в Hive/SQLite, synced_at = null)      │
     │                            │                      │                 │
     │  (появилась сеть)          │                      │                 │
     ├─POST /diary/bulk-sync ────▶│                      │                 │
     │                            ├─POST /diary/bulk-sync▶│                 │
     │                            │                      │◀──200 + list of │
     │                            │                      │    synced_ids ──│
     │                            │◀──200 + synced_ids ──▶│                 │
     │  (клиент помечает записи   │                      │                 │
     │   как синхронизированные)  │                      │                 │
     │                            │                      │──Event: diary.entry.created──▶│
     │                            │                      │                 │ (проверка паттерна
     │                            │                      │                 │  ухудшения: 3 дня
     │                            │                      │                 │  подряд балл ≤ 2)
```

**Описание:**
1. Пациент делает микро-отметку офлайн; запись сохраняется локально с `synced_at = null` и `device_id` (для идемпотентности).
2. При появлении сети клиент отправляет пакет записей через `POST /diary/bulk-sync`; дубликаты отфильтровываются по `device_id` + `recorded_at`.
3. `diary-service` принимает пакет, сохраняет новые записи, возвращает список синхронизированных `id`.
4. Для каждой новой записи публикуется событие `diary.entry.created`; `alert-service` проверяет паттерн ухудшения (например, 3 дня подряд низкий балл настроения) и при необходимости создаёт алерт.

### 5.3 Назначение упражнения врачом

```
Врач (React)                   API-шлюз                program-service      notification-service  Пациент (Flutter)
   │                             │                      │                  │                   │
   ├─POST /exercise-assignments ─▶│                      │                  │                   │
   │                             ├─POST /assignments ──▶│                  │                   │
   │                             │                      │◀──201 + id ──────│                  │                   │
   │                             │◀──201 + id ─────────▶│                  │                   │
   │                             │                      │──Event: assignment.created──▶        │
   │                             │                      │                  │◀──ack             │
   │                             │                      │                  │──Push: новое задание──▶
   │                             │                      │                  │                   ├─GET /assignments
   │                             │                      │                  │                   │ (просмотр плана)
```

**Описание:**
1. Врач назначает упражнение из библиотеки КПТ-материалов: выбирает тип, частоту, длительность курса.
2. `program-service` создаёт `ExerciseAssignment` и публикует событие `assignment.created`.
3. `notification-service` отправляет пациенту push-уведомление о новом задании.
4. Пациент видит задание в приложении, отмечает выполнение (`ExerciseCompletion`), при необходимости оставляет комментарий.
5. Невыполнение в заданный срок учитывается `program-service` и может формировать advisory-алерт врачу.

## 7. Индексы и ограничения базы данных

| Таблица | Индекс | Тип | Назначение |
|---------|--------|-----|------------|
| `users` | `idx_users_email` | UNIQUE | Поиск по email при входе |
| `users` | `idx_users_role` | B-tree | Фильтрация врачей/пациентов |
| `patient_profiles` | `idx_patient_profiles_clinic_id` | B-tree | Все пациенты клиники |
| `screening_results` | `idx_screening_results_patient_id` | B-tree | История скринингов пациента |
| `screening_results` | `idx_screening_results_is_critical` | B-tree | Быстрый поиск критических результатов |
| `diary_entries` | `idx_diary_entries_patient_id_recorded_at` | B-tree | График динамики по дате |
| `diary_entries` | `idx_diary_entries_synced_at` | B-tree | Офлайн-записи, требующие синхронизации |
| `exercise_assignments` | `idx_exercise_assignments_patient_id` | B-tree | Назначения пациента |
| `alerts` | `idx_alerts_patient_id_status` | B-tree | Активные алерты пациента |
| `alerts` | `idx_alerts_severity_created_at` | B-tree | Очередь алертов для уведомлений |
| `audit_logs` | `idx_audit_logs_user_id_created_at` | B-tree | Аудит действий пользователя |
| `audit_logs` | `idx_audit_logs_entity_type_entity_id` | B-tree | История изменений сущности |
| `medications` | `idx_medications_grls_id` | UNIQUE | Поиск препарата по ГРЛС |
| `prescriptions` | `idx_prescriptions_patient_id_status` | B-tree | Активные рецепты пациента |
| `medication_adherence` | `idx_adherence_prescription_id_taken_at` | B-tree | История приёма по рецепту |

Ограничения целостности:

- `screening_results.score` — CHECK: `score >= 0` (PHQ-9: 0–27, GAD-7: 0–21)
- `diary_entries.mood_score` — CHECK: `mood_score BETWEEN 1 AND 5`
- `diary_entries.anxiety_score` — CHECK: `anxiety_score BETWEEN 1 AND 5`
- `patient_profiles.consent_*` — NOT NULL (согласия должны быть явно проставлены при регистрации)
- Уникальность дубликатов в офлайн-синхронизации — частичный UNIQUE-индекс по (`device_id`, `recorded_at`, `patient_id`) в `diary_entries`
