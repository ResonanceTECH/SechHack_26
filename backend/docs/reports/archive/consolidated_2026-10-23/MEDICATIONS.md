# Лекарства и рецепты — модель данных и контуры доступа
**Источник:** `WP/White_Paper.MD` §4.2 (лекарства), экраны Figma (полный контур врача / сокращённый контур пациента), `docs/ChatExport_2026-10-20` (решения по источникам данных)  
**Статус:** MVP-решение без внешней интеграции

## 1. Ключевое решение
Данные по лекарственным препаратам в MVP **ведутся собственным справочником** в БД и заполняются администратором клиники. Интеграция с ГРЛС (и другими внешними реестрами) отложена — см. §5.
**Контуры доступа:**
- **Полный контур (врач):** состав, противопоказания, побочные действия, взаимодействия, инструкция, ссылка на первоисточник.
- **Сокращённый контур (пациент):** название, дозировка, схема приёма, статус назначения, отметки приёма, краткая инструкция «действие при пропуске», ссылка на инструкцию.
Сервер никогда не отдаёт пациенту поля `contraindications`, `interactions` и полный состав.

## 2. Модель данных
См. `DOMAIN_MODEL.md` §2 и `DB_SCHEMA.md` §2. Здесь — только правила предметной области.

### 2.1 `rx.medications` — справочник препаратов
| Поле | Обяз. | Правило |
|---|:---:|---|
| `name` | ✅ | Торговое название, как в реестре. Уникальность не жёсткая: допускаются одноимённые препараты разных производителей |
| `international_name` | ❌ | МНН — используется для поиска и группировки. Если совпадает у нескольких записей, `name` + `manufacturer` различают |
| `dosage_form` | ❌ | Справочник форм: таблетки, капсулы, раствор, ампулы, сироп, капли, суспензия, пластырь, инъекции |
| `strength` | ❌ | Например «10 мг», «20 мг/мл» |
| `manufacturer` | ❌ | Производитель |
| `instructions_url` | ❌ | Ссылка на официальную инструкцию (ОХЛП / aviandr.ru). Проверяется администратором перед сохранением |
| `contraindications` | ❌ | Полный контур только |
| `side_effects` | ❌ | Полный контур только |
| `interactions` | ❌ | Полный контур только |
**Дополнительные (вне БД, из локального справочника):** `patient_instruction` — краткое текстовое поле для пациента. В MVP хранится в `rx.medications` как отдельная колонка `patient_instruction TEXT` (добавляется миграцией) либо выводится из шаблона.

### 2.2 `rx.prescriptions` — назначение
| Поле | Обяз. | Правило |
|---|:---:|---|
| `patient_id` | ✅ | Пациент |
| `practitioner_id` | ✅ | Назначил врач |
| `medication_id` | ✅ | Препарат из справочника |
| `dosage` | ✅ | Дозировка: «10 мг», «2,5 мг» |
| `frequency` | ✅ | Частота: «2 раза в день», «на ночь» |
| `start_date` | ✅ | Дата начала |
| `end_date` | ✅ | Курс |
| `is_active` | ✅ | Флаг; закрытие назначения = `is_active=false` + запись в `audit_logs` |
**Бизнес-правила:**
- Назначение создаёт только пользователь с правом `prescription:write` (роль `doctor`; `psychologist` — нет)
- Снятие назначения — не удаление, а `is_active=false` (сохраняем историю)
- Одновременно активных назначений одного препарата у пациента быть не должно — предупреждение при создании

### 2.3 `rx.medication_adherence` — отметки приёма
| Поле | Обяз. | Правило |
|---|:---:|---|
| `prescription_id` | ✅ | Ссылка на назначение |
| `taken_at` | ✅ | Плановое время приёма (не фактическое) |
| `is_taken` | ✅ | `true` — принял, `false` — пропустил |
| `note` | ❌ | Заметка пациента: «было тошнотно» |
**Бизнес-правила:**
- Отметка может быть поставлена только владельцем назначения (`patient_id` совпадает) или врачом
- Уникальный индекс на `(prescription_id, taken_at)` — одна отметка на приём
- Расчёт adherence: `adherence = taken / planned` за период
- Три подряд пропущенных приёма → событие → алерт `adherence` с приоритетом `rx`

## 3. API-контракты

### 3.1 Полный контур — врач
`GET /api/v1/medications?search=сертраалин`
```json
{
  "data": [
    {
      "id": "m-1",
      "name": "Сертралин",
      "international_name": "сертралин",
      "dosage_form": "Таблетки",
      "strength": "50 мг",
      "manufacturer": "ОЗОН",
      "instructions_url": "https://aviandr.ru/...",
      "contraindications": "Одновременный приём ингибиторов МАО...",
      "side_effects": "Тошнота, диарея, бессонница...",
      "interactions": "Не сочетать с триптофанином..."
    }
  ],
  "meta": { "request_id": "...", "timestamp": "..." },
  "error": null
}
```

### 3.2 Сокращённый контур — пациент
`GET /api/v1/medications/{id}` в роли `patient`
```json
{
  "data": {
    "id": "m-1",
    "name": "Сертралин",
    "dosage_form": "Таблетки",
    "strength": "50 мг",
    "patient_instruction": "Принимать утром, до еды. При пропуске не принимать двойную дозу.",
    "instructions_url": "https://aviandr.ru/...",
    "is_prescribed": true,
    "adherence": 0.86
  },
  "meta": { "request_id": "...", "timestamp": "..." },
  "error": null
}
```
Поля `contraindications`, `side_effects`, `interactions`, `manufacturer` **отсутствуют** в ответе пациенту — это обеспечивается на уровне схем ответа (Pydantic `response_model`), а не только в коде роутера.

### 3.3 Назначение
`POST /api/v1/prescriptions`
```json
{
  "patient_id": "p-1",
  "medication_id": "m-1",
  "dosage": "50 мг",
  "frequency": "1 раз в день, утром",
  "start_date": "2026-10-20",
  "end_date": "2026-12-20"
}
```

### 3.4 Отметка приёма
`POST /api/v1/adherence`
```json
{
  "prescription_id": "p-1",
  "taken_at": "2026-10-20T08:00:00Z",
  "is_taken": true,
  "note": null
}
```

## 5. Источники данных и статус интеграции с ГРЛС

### 5.1 Что используется в MVP
| Источник | Допустимость | Что берём | Как |
|---|:---:|---|---|
| `aviandr.ru` (инструкции по применению) | ✅ Допустим | Инструкции по применению, разделы «Противопоказания», «Побочные действия», «Взаимодействие» | Ручной перенос в справочник администратором с сохранением ссылки `instructions_url` |
| `pharm-portal.ru` | ⚠️ Условно | Справочные данные по препаратам | Только при наличии auth key (официальный доступ) либо при юридической чистоте парсинга; **в MVP не используется** |
| ГРЛС (grls.rosminzdrav.ru) | ❌ Отложено | Реестровые данные о препаратах | Нет готового открытого API-контракта; требуется проработка условий использования |

### 5.2 Статус интеграции
Интеграция с ГРЛС **не входит в MVP**. Причины:
1. Отсутствует документированный публичный API с условиями использования.
2. Требуется юридическая оценка режима использования реестра.
3. Модель данных ГРЛС (приказ Минздрава № 341н) требует доработки наших сущностей: состав, регистрационное удостоверение, форма выпуска с вариантами, дозировки.

### 5.3 Что делаем вместо этого
- Собственный справочник `rx.medications` в БД, заполняемый вручную через `admin-service`
- Поля, критичные для клинической работы (противопоказания, взаимодействия, побочные), заполняются врачом/администратором со ссылкой на первоисточник в `instructions_url`
- Клиническая ответственность за содержимое справочника остаётся на клинике, что юридически корректнее автоматического импорта

### 5.4 План на будущее (не в MVP)
1. Запросить доступ к ГРЛС / выбрать легитимного поставщика данных о лекарствах.
2. Спроектировать промежуточный слой `medication_sync` (отдельная таблица сырых ответов + маппинг на `rx.medications`).
3. Версионировать справочник: `medication_versions` с датой актуальности и автором правки.
4. Добавить проверку взаимодействий при назначении (предупреждение врачу, не блокировка).

## 6. Ограничения MVP
- Автоматической проверки лекарственных взаимодействий нет — только текстовые поля, заполненные вручную
- Электронный рецепт (ЕГИСЗ) не интегрируется; рецепт — запись в БД
- Срок годности партии, учёт остатков в аптеке — вне периметра
- Проверка на дубли препаратов по МНН выполняется только как предупреждение в UI админки
