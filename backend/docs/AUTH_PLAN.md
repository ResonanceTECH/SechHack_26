# План аутентификации и авторизации (JWT + RBAC)

**Источник:** `ТЗ_Клинический_Компас_v1.0.md` §8.1, `WP/White_Paper.MD` §4.2 (роли), `docs/ChatExport_2026-10-20` (решения по ролям)  
**Статус:** MVP-решение

## 1. Решение

Собственная реализация JWT без внешнего IdP (Keycloak/Auth0 отложены). Обоснование — в §7.

**Два способа входа (вариант A):**

| Способ | Клиент | Идентификатор | Подтверждение | Пароль |
|---|---|---|---|---|
| **Телефон + SMS-код** | Мобильное приложение (React Native + Expo) | `phone` (`users.phone`) | 4-значный SMS-код, TTL 5 минут | Не требуется |
| **Email + пароль** | Веб-кабинет (React + Vite) | `email` (`users.email`) | — | Argon2id (§3) |

Оба способа выдают одинаковую пару access/refresh токенов (§2). Пользователь может иметь и email, и phone — вход возможен любым из них.

## 2. Схема токенов

| Параметр | Access token | Refresh token |
|---|---|---|
| Срок жизни | 15 минут | 7 дней |
| Формат | JWT (HS256) | JWT (HS256) |
| Хранилище на клиенте | только память (React/Vite, React Native — secure store) | secure storage (Keychain / EncryptedSharedPreferences) |
| Содержимое | `sub`, `role`, `clinic_id`, `jti`, `type=access`, `exp`, `iat` | `sub`, `jti`, `type=refresh`, `exp`, `iat`, `token_version` |
| Отзыв | Неявный по `exp` | Явный: запись в `refresh_tokens` + `token_version` пользователя |
| Передача | `Authorization: Bearer <access>` | Тело запроса `/auth/refresh` |

**Refresh rotation:** при каждом `/auth/refresh` старый refresh-токен помечается отозванным, выдаётся новая пара. При попытке повторного использования уже отозванного токена — отзыв **всех** refresh-токенов пользователя (признак компрометации) и запись в `audit_logs`.

## 3. Хеширование паролей

Пароль обязателен **только** для email+пароль входа (веб). Для телефон+SMS входа пароль не создаётся (`users.password_hash = NULL`).

- Алгоритм: **Argon2id** (`argon2-cffi`)
- Параметры MVP: `time_cost=3`, `memory_cost=64 MiB`, `parallelism=4`, `hash_len=32`, `salt_len=16`
- Политика пароля: минимум 10 символов, обязательны буквы разных регистров и цифра
- Сравнение: `argon2.PasswordHasher.verify()` (защита от timing-атак)
- Политика ротации: принудительная смена при подозрении на компрометацию, не по таймеру

## 3.1 SMS-код подтверждения телефона

| Параметр | Значение |
|---|---|
| Длина кода | 4 цифры |
| TTL | 5 минут (устанавливается врачом/системой; «Минут 5 на действие — это про кол для SMS») |
| Хранение | Одноразовый код: хеш в `sms_codes` (не хранится открытым), TTL, `is_used` |
| Повторная отправка | Rate limit: не чаще 1 раза в 60 секунд на номер |
| Проверка | Однократное использование; после успеха — `users.phone_verified = TRUE` |
| В проде | Интеграция с SMS-провайдером (SMSC, UniSMS); в dev — код логируется |

## 3.2 Invite-код привязки к врачу

Из обсуждения в команде (мобильный экран «Подключитесь к своему врачу»):

| Параметр | Значение |
|---|---|
| Алфавит | `23456789ABCDEFGHJKLMNPQRSTUVWXYZ` (32 символа: исключены только 0, 1, I, O — визуально неоднозначные; контракт с командой, без исключений) |
| Формат | `PREFIX-NNNNN`, например `RAV-27400`; дефис — **только маска в UI мобилки**, на бэкенд код приходит **без дефиса** (`RAV27400`) |
| Длина | Префикс врача/клиники + 5 символов из алфавита |
| TTL | Задаёт врач при генерации (срок действия приглашения) |
| Назначение | Привязка пациента к врачу: `POST /api/v1/auth/invite/verify` → `patient_assignments` |
| Уникальность | Гарантируется на уровне БД (partial UNIQUE-index по активным кодам); генерация с проверкой коллизий |
| Мультииспользование | Один код — несколько пациентов клиники (определяется флагом врача), либо одноразовый — решается настройкой врача |

**Способы ввода кода пациентом** (мобильное приложение, `mobile_dev`):

| Способ | Клиентский код | Что уходит на бэкенд |
|---|---|---|
| Ручной ввод | `RegisterDoctorScreen.onFindDoctor(code)` | `POST /api/v1/auth/invite/verify` с кодом без дефиса |
| QR-скан | `QrScanScreen` → `extractInviteCode()` (regex `[A-Z]{2,}-\d{3,}` вырезает код из QR-строки) | **тот же** эндпоинт — отдельный endpoint для QR не нужен, QR лишь экономит ручной ввод |
| Пропуск шага (`Skip`) | `onSkip` → регистрация без врача | привязка **опциональна**: пользователь создаётся без `patient_assignments`; invite-код можно ввести позже под активным JWT |

## 4. Таблицы сессий

DDL вынесен в `DB_SCHEMA.md` §1 (таблицы `refresh_tokens`, `sms_codes`, `invite_codes`, поле `users.token_version`).

Хранится только хеш refresh-токена: при компрометации БД восстановление токенов невозможно.

## 5. RBAC: роли и матрица прав

### 5.1 Роли

| Роль | Описание |
|---|---|
| `patient` | Пациент — мобильное приложение, свой контур данных |
| `doctor` | Врач — ведение пациентов, назначения, алерты |
| `psychologist` | Психолог — те же права, что у врача, без рецептов |
| `coordinator` | Координатор — администрирование записей, без клинических решений |
| `clinic_admin` | Администратор клиники — сотрудники, аналитика, аудит |
| `super_admin` | Системный администратор — все клиники, глобальные настройки |

### 5.3 Правила
- Права по умолчанию **отсутствуют** (deny by default)
- `self`-сущности ограничиваются дополнительно проверкой `resource.patient_id == current_user.patient_id`
- Роль проверяется на уровне dependency FastAPI (`require_roles(...)`, `require_permission(...)`)
- Доступ к медданным — только по служебной необходимости; в `audit_logs` фиксируется каждый GET по карточке пациента

## 6. Аудит доступа

В `audit_logs` фиксируются:

| Действие | Тип действия | Объект |
|---|---|---|
| Вход / выход / refresh | `auth.login`, `auth.logout`, `auth.refresh` | `User` |
| Изменение профиля пациента | `patient.update` | `PatientProfile` |
| Чтение карточки пациента | `patient.read` | `PatientProfile` |
| Назначение/отмена рецепта | `prescription.create`, `prescription.update` | `Prescription` |
| Закрытие алерта | `alert.resolve` | `Alert` |
| Смена роли сотрудника | `employee.role_change` | `User` |
| Выход из системы с отзывом токенов | `auth.revoke_all` | `User` |

Поля: `user_id`, `action`, `entity_type`, `entity_id`, `old_values`, `new_values`, `created_at`.  
Токены и пароли в `old_values`/`new_values` **никогда** не пишутся — используется whitelist полей.

## 7. Компромисс относительно Keycloak

| Критерий | Собственный JWT | Keycloak / внешний IdP |
|---|---|---|
| Скорость внедрения в MVP | ✅ Высокая — один сервис, без инфраструктуры | ❌ Низкая — отдельный сервис, realm-конфигурация, адаптеры |
| Один репозиторий, один деплой | ✅ | ❌ |
| SSO / федерация / MFA / «Войти через Госуслуги» | ❌ Нужна доработка | ✅ Из коробки |
| Централизованный каталог пользователей | ❌ Свой `users` | ✅ |
| Отзыв сессий | ✅ Через `refresh_tokens` и `token_version` | ✅ |
| Управление ролями из UI админки | ✅ Своя `admin-service` | ⚠️ Realm-конфигурация, слабее UX |
| Аудит | ✅ Собственный `audit_logs` | ⚠️ Отдельный механизм, другая модель |
| Итог | **Выбираем для MVP** | Отложено до этапа, когда появятся SSO/MFA и несколько продуктов |

**Когда вернуться к Keycloak:** появление SSO с внешними ИС, обязательная 2FA, несколько клиентов на разных стеках, соответствие стандартам ИБ клиник.

## 8. Защита эндпоинтов

| Мера | Реализация |
|---|---|
| Хеширование паролей | Argon2id |
| Защита от брутфорса | Rate limit: не более 5 попыток входа на email за 15 минут (Redis) |
| Защита от SMS-spam | Rate limit: не более 1 SMS в 60 секунд на номер; не более 5 SMS в час на номер |
| Защита от перечисления пользователей | Единый ответ 401 «Некорректный email или пароль» |
| HTTPS | Обязательно на уровне reverse proxy (nginx / Traefik) |
| CORS | Явный whitelist доменов из `\.env.example`, `credentials=True` |
| Заголовки | `X-Content-Type-Options: nosniff`, `Strict-Transport-Security`, `X-Frame-Options: DENY` |
| Ограничение размера тела | Middleware: максимум 1 MB (защита от DoS на bulk-sync) |
| Валидация входа | Pydantic v2: `EmailStr`, минимальная длина пароля, санитизация строк |
| SQL-инъекции | Только параметризованные запросы через SQLAlchemy Core/ORM |
| Утечки в ошибках | Единый обработчик: клиенту — `code` + `message`, в лог — полный traceback |
| Логирование | Структурированные JSON-логи (request_id, user_id, role, path, status, duration) |
| Маскирование ПД | В логах маскируются email, телефон, ФИО |

## 9. Ожидаемое поведение при ошибках

| Ситуация | HTTP | `error.code` |
|---|---|---|
| Нет токена / просрочен | 401 | `unauthorized` |
| Недостаточная роль | 403 | `forbidden` |
| Ресурс не принадлежит пользователю | 403 | `forbidden` |
| Неверный email/пароль | 401 | `invalid_credentials` |
| Rate limit | 429 | `rate_limited` |
| Ошибка валидации тела | 422 | `validation_error` |
| Не найдено | 404 | `not_found` |

## 10. Ограничения MVP

- Refresh-токен не хранится в `localStorage` веб-версии — только в памяти приложения
- Одновременная активная сессия на одном устройстве не ограничивается (лимит — 5 устройств на пользователя)
- Сброс пароля по email не реализован — администратор клиники сбрасывает пароль через `admin-service`
- 2FA / MFA — не входит в MVP
- Восстановление доступа при утере телефона — через администратора клиники (привязка нового номера)
- SMS-отправка в dev-окружении — заглушка (код пишется в лог сервера, не отправляется на реальный номер)
