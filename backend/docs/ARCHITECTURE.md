# Архитектура бэкенда — модульный монолит (MVP)

**Источник:** `ТЗ_Клинический_Компас_v1.0.md` §8, `Архитектурный_дизайн_моделей.md`, `Технологический_стек.md`  
**Статус:** черновик для реализации

## 1. Общая схема

```
┌─────────────────────────────────────────────────────────────┐
│                     Клиенты (мобилка / веб)                  │
│  React Native + Expo  │  React + Vite + TS                   │
└──────────┬────────────┬──────────────────────────────────────┘
           │ HTTPS / JSON
           ▼
┌─────────────────────────────────────────────────────────────┐
│                      API-шлюз (FastAPI)                      │
│  Routing • Аутентификация (JWT) • RBAC • CORS • Логирование  │
└──────────┬────────────┬──────────────────────────────────────┘
           │            │
   ┌───────┴───────┐ ┌──┴───────┐
   │ auth-service  │ │ patient- │
   │ patient-serv. │ │ service  │
   │ screening-s.  │ │ diary-s. │
   │ program-s.    │ │ alert-s. │
   │ admin-s.      │ │ notif-s. │
   │ audit-s.      │ │ med-s.   │
   └───────┬───────┘ └────┬─────┘
           │              │
   ┌───────┴───────┐ ┌────┴─────────┐
   │   PostgreSQL  │ │  PostgreSQL  │
   │   (одна БД)   │ │  (одна БД)   │
   │  concept01    │ │  concept02   │
   │  (общий)      │ │  (рецептур.) │
   └───────────────┘ └──────────────┘
           │
   ┌───────┴───────┐
   │    Redis      │
   │  (кеш + Celery)│
   └───────────────┘
```

## 2. Принципы

| Принцип | Реализация |
|---|---|
| **Модульный монолит** | Все сервисы в одном репозитории, чёткие границы модулей, возможность выноса в микросервисы позже |
| **Одна БД** | PostgreSQL; логическое разделение concept01 (общий) и concept02 (рецептурный); параметры подключения задаются через environment variables |
| **Синхронный API** | REST over HTTP (JSON), OpenAPI/Swagger через FastAPI |
| **Асинхронные события** | Redis Pub/Sub + Celery | Например, создание отметки дневника публикует событие `diary.entry.created`, на которое подписывается `alert-service`. |
| **Офлайн-синхронизация** | Оптимистичная репликация + флаг `synced_at` (мобилка хранит локально, отправляет пакет при сети) |
| **Минимально необходимый доступ** | RBAC, доступ к медданным только по служебной необходимости |

## 3. Модули (сервисы)

| Модуль | Ответственность | Контур | Технология |
|---|---|---|---|
| `auth-service` | Аутентификация, авторизация, JWT, роли, профили пользователей, согласия (152-ФЗ) | Общий | FastAPI + SQLAlchemy |
| `patient-service` | Данные пациентов, карточки, регистрация, согласия | Общий | FastAPI + SQLAlchemy |
| `screening-service` | PHQ-9, GAD-7 и другие скрининги, интерпретация результатов, подсчёт баллов | Общий | FastAPI + SQLAlchemy |
| `diary-service` | Микро-отметки дневника, графики, офлайн-синхронизация | Общий | FastAPI + SQLAlchemy |
| `program-service` | Назначенные упражнения, программы сопровождения, приверженность | Общий | FastAPI + SQLAlchemy |
| `alert-service` | Обнаружение критических симптомов, алерты врачу, план безопасности | Общий | FastAPI + Celery |
| `medication-service` | Данные по лекарствам (полная инфа врачу / упрощённая пациенту) | Общий (логически concept02) | FastAPI + SQLAlchemy |
| `notification-service` | Push (FCM), SMS, email-уведомления | Общий | FastAPI + Celery |
| `report-service` | Генерация отчётов о динамике, PDF-экспорт, аналитика клиники | Общий | FastAPI |
| `admin-service` | Управление ролями, правами, тарификацией, настройками клиники | Общий | FastAPI |
| `audit-service` | События доступа и изменения критических данных | Общий | FastAPI |

## 4. Механизмы взаимодействия

| Тип | Механизм | Описание |
|---|---|---|
| Синхронный запрос-ответ | REST over HTTP (JSON) | Клиент → API-шлюз → модуль. Все эндпоинты документируются через OpenAPI/Swagger. |
| Асинхронные события | Redis Pub/Sub + Celery | Например, создание отметки дневника публикует событие `diary.entry.created`, на которое подписывается `alert-service`. |
| Изоляция контуров | Логическое разделение в одной БД | Рецептурный контур не имеет прямого доступа к таблицам общего контура; обмен только через DTO и строго определённые контракты. |
| Офлайн-синхронизация | Оптимистичная репликация + `synced_at` | Мобильный клиент хранит локально (AsyncStorage), при появлении сети отправляет пакет изменений с метками времени. |

## 5. Что НЕ делаем на старте

- Выделение concept02 в отдельную БД — только логическое разделение
- Keycloak / OIDC — только собственные JWT
- Парсинг ГРЛС через API — данные по лекарствам согласно экранам Figma
